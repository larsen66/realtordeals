# Предложение API-контракта для Давида

Статус: клиент реализован в apps/bot, серверные маршруты пока отсутствуют. Не считать этот документ уже согласованным/развернутым API. При отличии фактических маршрутов Давида меняем адаптер http.ts, не создаем второй сервер.

## Владение

- Вера: apps/bot/**, apps/worker/src/agent/**, этот документ и docs/product/bot-behavior.md.
- Давид: apps/api/**, packages/domain/**, остальной worker, миграции, Redis, S3, общие manifests, lockfile, Docker/CI и общие инструкции.
- Роман: состав полей и правила рабочего процесса.

В этой ветке общие файлы, API, веб и доменная модель не изменены. Общий pnpm-lock.yaml намеренно не обновлен: Давид делает это один раз после проверки нового apps/bot/package.json.

## Авторизация и повторные запросы

Все маршруты — внутри существующего Express API. `Authorization: Bearer <CRM_API_TOKEN>` — сервисный токен бота. `X-Telegram-User-Id`, `X-Telegram-Chat-Id` задают менеджера/контекст, но доверять им можно только после проверки сервисного токена и разрешенного менеджера. Чужие карточки недоступны. Идентичность конкретного бота определяется сервером по учетным данным.

POST содержит `Idempotency-Key`. Сервер сохраняет результат вместе с изменением состояния; ключи ограничены учетными данными бота и менеджером. Повтор не добавляет второй исходник, задание или карточку. Ключ сообщения: `telegram:<userId>:<updateId>`. Подтверждение: `confirm:<draftId>:<revision>`. Создание: `new:<chatId>:<menuMessageId>:<role>`.

## Маршруты

| Метод/путь | Тело | Ответ |
| --- | --- | --- |
| GET /bot/v1/drafts/current | — | Draft или null |
| POST /bot/v1/drafts | `{role: "buyer" или "seller"}` | Draft |
| GET /bot/v1/drafts/:id | — | Draft |
| POST /bot/v1/drafts/:id/messages | InputMessage | Draft, обычно processing; можно HTTP 202 |
| POST /bot/v1/drafts/:id/confirm | `{revision, confirmed: true}` | Draft со status=confirmed и cardId |

Успешное подтверждение сохраняет номер подтвержденной revision. Новая карточка и результат идемпотентности фиксируются в одной транзакции. Повтор проверки/нажатия возвращает тот же cardId. Версия меняется при изменении полей/ошибок/входящих данных, а не из-за чтения. Новое сообщение немедленно инвалидирует старый предпросмотр, еще до результата ИИ.

Ошибки: 401/403 — доступ; 409 — устаревшая версия/конфликт; 422 — поля не прошли проверку; прочие сбои — недоступность. Клиент не показывает пользователю сырые тела ошибок и не переходит в демо автоматически.

## DTO Draft — представление для бота

```json
{
  "id": "draft_01",
  "revision": 3,
  "role": "buyer",
  "status": "needs_input",
  "fields": [
    {"key": "name", "label": "Имя", "value": "Учебный клиент"},
    {"key": "phone", "label": "Телефон", "value": null}
  ],
  "issues": ["Нужен телефон"],
  "notes": [],
  "canConfirm": false,
  "cardId": null
}
```

id: 1–36 символов A–Z/a–z/0–9/_/-. revision: целое от 0 до 2147483647. Статусы: collecting, processing, needs_input, ready, confirmed. Поля value — отформатированные строки или null; реальную типизированную модель хранит сервер. fields, issues, notes возвращаются полностью. canConfirm=true только для ready без issues; confirmed требует cardId и canConfirm=false.

Это DTO отображения, не копия buyer/seller схем. Порядок и названия полей дает API. Бот не вычисляет обязательность и не приводит денежные суммы/площади к своим форматам.

## InputMessage

```json
{"kind":"text","text":"Учебный текст","messageId":1,"updateId":100}
```

```json
{
  "kind":"voice", "fileId":"telegram-file-id", "fileUniqueId":"unique-id",
  "size":512, "duration":30, "mimeType":"audio/ogg", "messageId":2, "updateId":101
}
```

size может быть null. Бот передает fileId, не URL с Telegram-токеном. Worker получает файл с учетными данными того же Telegram-бота, проверяет фактический размер, тип и ограничения, сохраняет исходник в закрытое хранилище. Конкретный загрузчик и его секреты — зона Давида; в этой ветке его нет.

## Очередь и OpenAI

1. API сохраняет исходник и сообщение, связывает с draftId/managerId и новой revision; надежно ставит задачу без потери между БД и очередью.
2. Worker берет актуальную схему нужной роли из packages/domain. Для извлечения допускаются неизвестные/неполные поля; окончательная обязательность проверяется отдельно.
3. Для голоса вызывает `OpenAiAgent.transcribe(file)`; сохраняет транскрипт. Для текста использует исходник.
4. Вызывает `OpenAiAgent.extract({role, sourceText, currentFields}, {jsonSchema, parse})`. Модуль Веры уже реализован, модели и ключ передаются явно из серверной конфигурации. JSON Schema должна поддерживать strict Structured Outputs и неразобранные заметки/вопросы.
5. Проверяет результат общей схемой; применяет с контролем revision и порядка сообщений. Старое задание не затирает новые исправления. При конфликте актуальный контекст собирается заново.
6. Обновляет Draft: поля, ошибки, заметки, статус и canConfirm. Не создает подтвержденную карточку по ответу модели.

В конфигурации worker нужны OPENAI_API_KEY и выбранные имена моделей (например OPENAI_TEXT_MODEL и OPENAI_TRANSCRIPTION_MODEL — имена переменных закрепляет Давид). Модуль не читает env сам и не содержит ключей/значений моделей по умолчанию. Корневой .env.example в этой ветке не меняется.

Бот опрашивает состояние только для обновления UI, до минуты. Очередь и данные остаются на сервере. Надежная доставка результата после перезапуска бота пока не реализована; пользователь восстанавливает экран через /draft. Напоминания к этому UI-таймеру не привязывать.
