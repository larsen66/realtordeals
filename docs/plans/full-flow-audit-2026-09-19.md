# Проверка БД, API и CRM

Дата: 2026-09-19.
Проверка выполнена на локальных Next.js :3000, Express :3001 и Supabase :55421 с PostgreSQL в контейнере `supabase_db_rieltordeals`.
Production и внешняя доступность API не проверялись.

## Вывод

Основной ручной контур CRM работает: создание покупателя и продавца, запись полей в PostgreSQL, чтение карточек, изменение этапа, создание и выполнение задач, завершение обещанного звонка.
Полный продуктовый поток пока не завершён: лендинг, приём лидов, файлы, бот и фоновые обработки не реализованы.
Остаются существенные риски перезаписи устаревших данных и отсутствия авторизации API.

```text
CardForm / TaskEditor в браузере
        | POST/PATCH через apps/web/src/lib/cards.ts и tasks.ts
        v
apps/api/src/index.ts -> Express routes/cards.ts
        | проверка packages/domain -> cards/input.ts
        v
cards/supabase-store.ts -> cards/map.ts -> PostgreSQL public.cards
        | GET /cards и GET /cards/:id
        v
Next.js страницы CRM -> списки / панель / полная форма
```

Express и Next.js работают как серверные процессы и после запроса не завершаются.
Команды тестов и сборки завершаются после выполнения проверок.

   До исправления переход из панели нового продавца по кнопке добавления покупателя менял заголовок, но сохранял роль продавца и его поля.

## Оставшиеся проблемы

### P1: устаревшая форма перезаписывает новую правку

Воспроизведено двумя реальными вкладками на одной тестовой карточке.
Форма отправляет только изменения без версии, которую видел менеджер: `apps/web/src/components/crm/card-form.tsx:149`.
Обработчик получает текущую версию непосредственно перед записью, поэтому существующая проверка защищает только пересекающиеся серверные операции: `apps/api/src/routes/cards.ts:44` и `:62`.
Нужно передавать версию исходной карточки и явно обрабатывать конфликт на фронте.
Нынешний зелёный тест конкурентных записей проверяет store, а не этот сценарий двух устаревших форм.

### P1 до публикации: API не требует авторизации

GET, POST и PATCH /cards доступны без cookies или Authorization в проверенном локальном API.
`apps/api/src/app.ts:12` подключает CORS и маршруты без auth middleware.
`apps/api/src/lib/supabase.ts:5` использует service-role ключ, поэтому RLS не ограничивает клиентов Express.
Нужно определить вход менеджеров и серверную проверку доступа перед открытием API наружу.
Проверка не устанавливает, открыт ли текущий сервер публично или защищён внешним шлюзом.

### P2: списки ограничены лимитом Supabase

`apps/api/src/cards/supabase-store.ts:10` делает один запрос без пагинации.
`supabase/config.toml:18` задаёт max_rows=1000.
Следствие по коду: при превышении лимита часть карточек не попадёт в списки, поиск и расчёт задач на фронте.
Массовое наполнение БД для воспроизведения не выполнялось.

### P2: время задач зависит от часового пояса процесса

`apps/web/src/lib/cards.ts:97` форматирует дату без явного timeZone.
`apps/web/src/lib/tasks.ts:48` определяет «сегодня» через локальный toDateString процесса.
Редактор datetime-local использует часовой пояс браузера.
Следствие по коду: при разных поясах сервера и браузера отображение времени и границы «Сегодня» могут различаться.
Сценарий отдельного сервера в UTC не проверялся.
Нужно согласовать бизнес-пояс и использовать его для отображения и фильтрации.

### P2: сбой API выглядит как отсутствующая карточка

`apps/web/src/components/crm/card-details.tsx:14` перехватывает любую ошибку getCard и вызывает notFound().
Это подтверждено чтением кода; действующий общий API намеренно не выключался.
Нужно различать ответ 404 и недоступность сервера.

### Дополнительные ограничения контракта

- Телефон проверяется только на непустую строку: `packages/domain/src/persist.ts:7`.
- Подтверждение создания существует только в UI, а API не хранит факт подтверждения менеджером.
- POST /cards не имеет ключа идемпотентности.
- Смена роли через API не определяет правила очистки полей другой роли; интерфейс блокирует изменение роли существующей карточки.
